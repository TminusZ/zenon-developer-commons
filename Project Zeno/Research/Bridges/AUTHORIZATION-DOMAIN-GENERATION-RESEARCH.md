# Can an Authorization Domain Be Generated? A First-Principles Investigation

## 0. Method and epistemic labeling

This document does not try to validate the idea that Authorization Domains could be generated. It tries to break it, and reports what survives.

Four labels are used throughout, inline, wherever the status of a claim is not obvious from context:

**[FACT]** — a verifiable fact: about Project Zeno's current specification, about a named external system's actual mechanics, or about documented prior art, checked against a source rather than recalled from impression.
**[CONCLUSION]** — a reasonable architectural inference drawn from stated facts by ordinary reasoning, offered as sound but not as proven.
**[SPECULATIVE]** — a plausible direction that has not been tested, prototyped, or reviewed, offered as a hypothesis worth investigating rather than a design decision.
**[OPEN]** — a question this document raises and does not resolve.

The four architecture elements assumed, per the prompt, are the ones already established elsewhere in this repository: a Settlement Layer that understands only Settlement-native authorizations; Execution Domains that run general computation; Authorization Domains that translate externally verifiable evidence into those authorizations; and a Settlement Layer that remains chain-agnostic by construction. Nothing in this document revises that model. It asks a narrower question about how the second-to-last of those four pieces gets built.

---

## 1. What would an Authorization Domain need to know about an external chain?

**[FACT]** The Interoperability Design Principles document already decomposes any Interop design into seven layers: Verification, Accounting, Messaging, Custody, Enforcement, DA and proof availability, and Phase status. That decomposition is the right starting scaffold for this question, because several items on the prompt's candidate list belong to different layers than they first appear to, and conflating layers is precisely the error that decomposition exists to prevent.

Sorting the prompt's candidate list against that scaffold:

**Verification-layer fields (what the domain STF must check to accept a piece of external evidence as genuine):** consensus algorithm class, finality model, header structure, Merkle (or Merkle-Patricia, or other) commitment structure, signature scheme(s), fork-choice rule, chain reorganization depth/rules, light-client trust assumptions, witness structures, inclusion-proof format. These are the fields that determine whether a given piece of relayed data could have come from the real chain at all.

**Accounting-layer fields (what the domain does once it believes the evidence):** transaction format (specifically, which parts of it identify a deposit as belonging to this Authorization Domain, e.g. watched scripts/addresses for Bitcoin, event/log signatures for Ethereum-style chains), event model, state model (only the parts relevant to representing a claim, not the chain's full state semantics).

**Custody-layer fields, explicitly out of an Authorization Domain's own scope per the design principles document's own boundary ("verification is not custody"):** scripting model, execution model, and block-production mechanics beyond what finality depends on. These matter enormously to the separate, unspecified custody mechanism (a Bitcoin-side BitVM-style protocol needs to know Bitcoin's scripting model intimately; an Ethereum lockbox contract needs to know the EVM), but they are not inputs to the Authorization Domain's own STF, which only verifies and accounts. Putting them in the same "chain description" as the verification fields would blur exactly the boundary the design principles document exists to hold.

**[CONCLUSION]** The minimal complete set for the verification layer specifically, the layer this document is actually about, is:

A consensus-family identifier (which class of finality argument applies: probabilistic-depth proof-of-work, deterministic BFT quorum certificate, checkpoint-with-rotating-committee, or another named class). A header/commitment byte layout (field order, widths, and which fields feed which hash). A hash function reference. A signature-scheme reference (or references, since finality-checkpoint chains typically layer an aggregate scheme over an underlying one). A Merkle (or equivalent) proof structure reference, including branching factor and any domain-separation prefixes. A finality predicate: for probabilistic chains, a confirmation depth; for deterministic chains, a quorum threshold and validator-set reference; for checkpoint chains, a committee-rotation period and trust-level fraction. A validator-set (or difficulty-set) update rule, since almost every consensus family's light-client problem reduces to "how do I safely learn the next set of things I should trust," not merely "how do I verify one header." A reorg/fork-choice tie-break rule, needed to reject or defer to a competing chain of evidence. A deposit-identification predicate (accounting layer, but load-bearing enough to belong on any complete list): the rule by which the STF decides a given verified event is a deposit meant for this Authorization Domain and not unrelated chain activity.

That is nine fields, not the seventeen the prompt lists as candidates, because several of the prompt's candidates (scripting model, execution model, block production beyond finality) are custody- or curiosity-layer information that a verification-only Authorization Domain does not need to carry.

**[OPEN]** Whether "consensus-family identifier" is itself a closed, enumerable set, or an open one that keeps needing new members as genuinely novel consensus designs appear, is unresolved and returns in Section 7.

## 2. Can this be expressed as a Chain Configuration / Driver Specification?

**[CONCLUSION]** Yes, in the sense that the nine-field list above is already mostly the kind of thing a declarative record can hold: fixed-width identifiers, byte offsets, algorithm references, numeric thresholds. Whether it can be expressed *entirely* declaratively is a different and harder question, addressed here by separating what should be declarative data from what almost certainly has to remain executable logic.

**Declarative (data, not procedure):** the hash function reference; the signature-scheme reference; the header byte layout (as an ordered list of named, fixed- or length-prefixed fields); the Merkle proof structure's branching factor and sibling-ordering convention; the finality predicate's numeric parameters (confirmation depth, quorum fraction, committee period); the consensus-family identifier itself, understood as a selector rather than a description.

**Executable (procedure, not data), even in an aggressively generation-friendly design:** the fork-choice tie-break algorithm, because "which of two competing valid-looking chains wins" is a comparison procedure over headers, not a static value; the validator-set (or difficulty) update rule, because it is a state-transition function in its own right, not a constant; the deposit-identification predicate, because it typically involves pattern-matching against chain-specific address or event formats that do not reduce to a fixed-width field; and misbehaviour/equivocation handling, because it is a procedure over two conflicting pieces of evidence, not a value.

**[CONCLUSION]** This split is not arbitrary; it falls along almost exactly the same line TableGen (Section 8) draws between what a `.td` file specifies and what remains hand-written C++, and along almost exactly the same line IBC's `ClientState`/`ConsensusState` interface draws between the data a light client module stores and the `verifyHeader`/`updateState`/misbehaviour functions it must implement. That three-way convergence, arrived at independently here and observed empirically in two unrelated existing systems, is itself evidence that the boundary is close to a natural one rather than an artifact of this document's particular framing.

**Reusable primitives** that a Chain Configuration could plausibly select and parameterize rather than each Authorization Domain reimplementing from scratch: a fixed-width and length-prefixed header parser, generic over field layout; a Merkle inclusion/non-inclusion verifier, generic over hash function and branching factor (Project Zeno's own SMT core is already exactly this kind of thing, generic over path width and hash choice, per `SPEC.md` §13); a Merkle-Patricia trie verifier for account/receipt/storage proofs, generic over the same axes; a set of signature verifiers, one per scheme (ECDSA/secp256k1, ed25519, BLS12-381 aggregate), each usable by any chain that happens to use that scheme; a proof-of-work difficulty verifier, generic over target encoding; a BFT quorum-certificate verifier, generic over validator-set representation and threshold.

**[SPECULATIVE]** `SPEC.md` §6 already carries a field, `stfSpecHash`, described as pinning "runtime kind, runtime/VM version, genesis state, input-envelope + commitment format" but, per a prior review of this spec stack, never given a concrete derivation formula. For an Authorization Domain specifically, `stfSpecHash` could plausibly be, or include, the hash of exactly the declarative Chain Configuration record described above. This would give the configuration the same content-addressing property `code_hash`/`CodeHash` already give WASM contracts: a verifier could confirm what configuration a running Authorization Domain claims to implement without trusting the operator's say-so. This is a genuinely open design opportunity, not a proposal this document is in a position to finalize, since it depends on resolving the `stfSpecHash` derivation question at the level of `SPEC.md` itself, which is outside this document's scope.

## 3. Which portions are generic? Which are chain-specific?

**[FACT]** `EXECUTOR.md` already defines a generic `Domain` interface every domain, Authorization Domains included, must satisfy: a genesis-state constructor, an input decoder, and a pure state-transition function, with the runtime supplying ordering, witnessing, batching, and commitment machinery identically regardless of what the domain computes. This is, in effect, an existing driver interface. The question this section asks is how much of what fills that interface, specifically the decode and STF logic for an externally-facing domain, could become generic code parameterized by configuration, versus how much has to stay bespoke per chain.

**[CONCLUSION]** The honest boundary runs along a distinction between syntactic generality and semantic specificity, and it is worth stating plainly because it is the single most load-bearing conclusion in this document.

**Syntactically general (a strong candidate for configuration-driven reuse):** parsing a header into named fields; computing and checking a hash over those fields; verifying a Merkle or Merkle-Patricia inclusion proof against a committed root; verifying a signature or aggregate signature against a known key set; checking a numeric finality threshold. None of this requires understanding what the chain is *for*. It requires only understanding the shape of its data.

**Semantically specific (a poor candidate, likely to remain handwritten):** deciding what counts as a valid deposit for this Authorization Domain, given the chain's particular way of representing ownership (a Bitcoin UTXO paying a watched script bears no structural resemblance to an Ethereum event log matching a topic signature, even though both are, at the syntactic level, "a proof of an event against a committed root"); deciding what a reorg deep enough to matter actually means for this chain's specific security assumptions; deciding how a validator-set or difficulty transition is triggered and what its own integrity conditions are, since this is frequently the most chain-idiosyncratic part of any consensus design.

**[CONCLUSION]** Put in one sentence: the parts of an Authorization Domain that ask "is this evidence real" look generalizable; the parts that ask "what does this evidence mean" do not, because meaning is exactly the thing that differs chain to chain, and no declarative schema can carry semantics it was never given a vocabulary for. This is not a claim that meaning could never be captured by a richer schema; it is a claim that the schema would then need to be closer to a small domain-specific language than to a flat configuration record, at which point the question of whether it counts as "declarative" starts to blur, a tension returned to in Section 7.

## 4. Comparison to six existing analogies

Each candidate analogy is scored on two axes: does the real-world system already achieve automated generation from a declarative description, or only a common interface with handwritten implementations behind it; and does the domain it operates in have anything close to blockchain consensus's degree of underlying diversity.

**Device drivers.** **[FACT]** Real operating-system driver models (Linux's driver model, Windows's WDF, and Linux's Device Tree mechanism specifically) mostly use declarative description to *select and parameterize* a driver, not to generate its verification/protocol logic. Device Tree tells the kernel which driver binds to which piece of hardware and what resources (addresses, interrupts, clocks) it has; the driver's actual protocol handling remains hand-written C. **[CONCLUSION]** This is a strong analogy for the *architectural shape* this document has been building toward (a small set of hand-written, reused primitives, selected and parameterized by declarative data, behind one interface the core never has to grow to accommodate) but a weak analogy for evidence of *generation specifically*, since real driver ecosystems do not generate driver logic from a device description either.

**Compiler backends (LLVM/TableGen).** **[FACT]** TableGen is a declarative language (`.td` files) describing a target's registers, instructions, and encoding; it is combined with the hand-coded C++ files from the backend, and TableGen's various backends generate register-file information, instruction definitions, and code-emitter functions, while instruction *selection*, *scheduling*, and *legalization* logic remain substantially hand-written, target by target. **[CONCLUSION]** Of the six candidates, this is the strongest analogy for the specific question this document investigates, because it is the only one that already demonstrates real, working, partial generation from declarative description in a domain with a genuinely comparable degree of underlying irregularity (dozens of real-world instruction set architectures, no two alike, much as dozens of real-world consensus designs are no two alike), and because the boundary it draws between generated and handwritten code lands in almost the same place Section 2 of this document independently arrived at.

**Protocol adapters (IBC light client modules; LayerZero's DVN/adapter model; Axelar).** **[FACT]** IBC's `ClientState`/`ConsensusState`/`ClientMessage` interface (ICS-02, ICS-07) is a standardized, multi-year-mature interface that any new light client type must implement; in practice, each type (07-tendermint, 06-solomachine, 11-beefy for Substrate/Polkadot parachains) is a separate, substantial, hand-written engineering effort. LayerZero V2 similarly standardized on a pluggable "Decentralized Verification Network" role behind a common Endpoint interface, with each DVN (including at least one, Polyhedra's, built on a zk light client) independently engineered. **[CONCLUSION]** This is strong evidence that the *interface* pattern this document has been assuming (one common shape, many chain-specific implementations behind it) is real, load-bearing, and already proven at production scale across a genuinely diverse set of chains. It is simultaneously the strongest available evidence *against* optimism about generation, addressed further in Section 9, since none of these mature, well-funded, multi-year projects has achieved implementation-level generation, only interface-level standardization.

**Database drivers (ODBC/JDBC).** **[CONCLUSION]** This analogy is instructive precisely because of where it differs from the blockchain case, not where it agrees. ODBC and JDBC succeed at "swap the configuration, not the code" because SQL itself is an already-converged semantic standard that essentially every relational database already implements compatibly; the driver's job is mostly dialect translation over a shared foundation, not fundamentally different verification logic. Blockchains have no equivalent converged foundation. There is no "SQL of consensus" that Bitcoin, a BFT chain, and a checkpoint-committee chain already all speak variations of. **[CONCLUSION]** This suggests generation will be structurally harder for Authorization Domains than for database drivers, not merely harder in degree, because the database case benefits from a semantic convergence the blockchain case does not have and has no obvious path to acquiring.

**Language runtimes (JVM, WASM as portable compilation targets).** **[CONCLUSION]** This is a weaker fit than it first appears, and largely for a reason worth naming explicitly: this analogy describes *execution* portability, many source languages compiling to one bytecode target, which is closer to what Project Zeno's own multi-VM Execution Domain model already does (many runtimes settling to one interface) than to what an Authorization Domain does (many external *consensus systems* being *verified* into one interface). The directions of translation are inverted. Noting this sharpens rather than weakens the rest of this document: Execution Domains and Authorization Domains, though structurally identical as domains, are solving analogically different problems, one about running code portably, the other about believing evidence portably, and the runtime analogy belongs to the former.

**Network stacks (OSI/TCP-IP layering).** **[CONCLUSION]** A moderate fit for the *separation-of-concerns* half of this document's thesis (the network layer does not need to know whether the link layer is Ethernet or Wi-Fi, exactly as Settlement does not need to know whether the Authorization Domain beneath it is verifying Bitcoin or a BFT chain) and a weak fit for the generation question specifically, since layering addresses who needs to know what, not whether a given layer's logic can be produced automatically from a description of the layer beneath it.

**Verdict on this section: [CONCLUSION].** Compiler backends are the strongest analogy for the generation question specifically. Device drivers and protocol adapters are the strongest analogies for the architectural shape, but the protocol-adapter evidence, examined closely, argues against near-term generation rather than for it.

## 5. Comparison table: Bitcoin, Ethereum, Solana, and a Tendermint/CometBFT-based chain

A fourth chain was chosen deliberately for maximum structural contrast on the axis that matters most to this document, finality model, rather than for market prominence: a generic Cosmos SDK chain running CometBFT consensus has deterministic, single-block finality, an axis neither Bitcoin (probabilistic, depth-based) nor Ethereum (checkpoint-based, roughly two epochs) nor Solana (vote-lockout-based, currently roughly thirteen seconds) currently occupies.

| Field | Bitcoin | Ethereum | Solana (current, pre-Alpenglow) | Tendermint/CometBFT chain |
|---|---|---|---|---|
| Consensus family | Proof-of-work, longest valid chain | Proof-of-stake, Casper FFG finality gadget + LMD-GHOST fork choice | Proof-of-stake, Tower BFT vote-lockout over a Proof-of-History clock | Classical BFT, one round of pre-vote/pre-commit among a known validator set |
| Finality model | Probabilistic, deepens with each confirmation | Checkpoint finality, roughly every two epochs (~12–15 min) | Vote-lockout finality; **[FACT]** roughly 12.8 seconds today, with a validator-approved upgrade (Alpenglow, passed governance September 2025) targeting ~100–150 ms, not yet on mainnet as of this writing | Deterministic and instant: a block with a valid 2/3-plus-voting-power quorum certificate is final, no depth required |
| What a light client actually verifies | Header chain plus proof-of-work plus a Merkle inclusion proof against a block's transaction root | **[FACT]** A 512-member sync committee's aggregated BLS signature over a beacon-chain header, plus a Merkle proof (SSZ) against the beacon state, with the committee rotated roughly every 27 hours | Vote/lockout history is not a mature light-client target today; verification is feasibility-first per the project's own Interop research, driven by validator-set size and account-proof format | **[FACT]** A quorum certificate: aggregate or batched signatures from a known, explicitly enumerated validator set signing the header directly (the basis of IBC's 07-tendermint client) |

| Custody feasibility (explicitly a separate question from verification) | No general computation; custody requires a key-holding party, a threshold scheme, or a BitVM-style challenge protocol | General computation available; an Ethereum-side lockbox contract is a plausible custody mechanism | General computation available; a Solana-side program is a plausible custody mechanism, unstudied here | General computation available in most Cosmos SDK chains; a chain-side module is a plausible mechanism |

**[CONCLUSION]** The table's most important cell, for this document's purposes, is not any single chain's row but the observation that "consensus family" and "custody feasibility" vary almost independently of each other: Bitcoin's verification is comparatively simple and its custody comparatively hard; a CometBFT chain's verification is comparatively simple and its custody comparatively easy; Ethereum is moderate on both; Solana's verification is presently the least mature of the four for light-client purposes specifically, independent of custody entirely. This independence is itself evidence that "one chain description" cannot collapse into "one difficulty score," which matters for how a future driver specification should be scoped.

## 6. Fork inheritance

**[CONCLUSION, grounded in FACT] Bitcoin-family forks** (chains sharing Bitcoin's header format, transaction format, and PoW-based longest-chain rule, differing mainly in genesis parameters, difficulty-adjustment constants, and sometimes the hash function itself) would inherit nearly the entire Chain Configuration described in Section 2 unchanged: header layout, Merkle structure, and fork-choice rule are identical by construction. The one field genuinely worth stress-testing is the hash function reference: a well-designed configuration schema treats it as a pluggable primitive selection rather than a hardcoded assumption, precisely because some Bitcoin-family forks (historically, chains using Scrypt rather than SHA-256d) differ on exactly this axis and nothing else. A configuration schema that could not express "same shape, different hash primitive" would have failed its first real test.

**[CONCLUSION] Ethereum forks are a more interesting and less generous case than the prompt's phrasing suggests.** Most chains popularly described as "Ethereum forks" (EVM-compatible chains with their own independent validator sets and consensus mechanisms) are execution-compatible, not consensus-compatible. The Interoperability Design Principles document already states this distinction directly: runtime compatibility is not liquidity, and by the same logic it is not consensus compatibility either. An Authorization Domain built against Ethereum's beacon-chain sync-committee model would not transfer to an EVM-compatible chain running its own independent validator set and its own finality rule, because the entire verification layer, the part this document has argued is the more generalizable half, is exactly the part that differs. Only a chain that is a *literal* fork of Ethereum's consensus client, inheriting the beacon chain, the sync committee, and the same finality gadget, would inherit the configuration wholesale, and such forks are rare.

**[FACT, strong evidence] Cosmos SDK chains built on CometBFT constitute the strongest real-world case for high inheritance available anywhere in this document.** IBC's own production history already demonstrates it: a single 07-tendermint light client module type is used, essentially unmodified in its verification logic, across the entire ecosystem of independently sovereign Cosmos SDK chains, because they share CometBFT consensus verbatim. What differs chain to chain is the accounting layer (asset registries, denomination formats, application-specific modules), exactly the layer Section 3 already predicted would remain bespoke, not the verification layer.

**[FACT, corroborating evidence] Substrate/Polkadot parachains show the same pattern from a different direction.** A single BEEFY-based light client instance can prove finality for every parachain connected to one relay chain, because parachains inherit consensus from the relay chain rather than each running an independent one; the verification work is done once, at the relay-chain level, and shared.

**[CONCLUSION]** Across all four cases, the pattern is consistent enough to state as a general rule: inheritance is high wherever chains share a consensus family by construction (Cosmos SDK chains under CometBFT, parachains under a shared relay chain, Bitcoin-family forks sharing PoW/header mechanics) and low wherever "family resemblance" is actually execution-layer compatibility mistaken for consensus-layer compatibility (most EVM-compatible chains relative to Ethereum's own beacon chain). Estimating "how much work would need changing" is therefore not a percentage that applies uniformly across "forks" as a category; it is close to zero for genuine consensus-sharing families and close to total for chains that merely resemble each other at the execution layer.

## 7. Where does generation stop?

**[CONCLUSION]** Synthesizing Sections 1 through 6: there is enough common structure for the *verification* layer's *syntactic* components, within an already-known consensus family, to be meaningfully configuration-driven rather than handwritten from scratch for every new chain. There is not, on current evidence, enough common structure for full generation of an Authorization Domain, for three independent reasons.

First, **the class problem**: configuration-driven reuse only helps for the Nth chain within a consensus family someone has already modeled. The first chain of a genuinely novel consensus design (a design that isn't proof-of-work, isn't a BFT quorum certificate, isn't a checkpoint-with-rotating-committee, isn't some already-catalogued variant) requires the same greenfield engineering a generation framework was meant to avoid, because there is nothing yet to select and parameterize. This means the value of any such framework is backloaded onto chains most similar to ones already studied, and front-loaded work (studying and modeling the first instance of each family) never goes away.

Second, **the semantic problem** from Section 3: accounting-layer logic, what counts as a valid deposit given this chain's particular representation of ownership, resists reduction to a flat configuration record because it requires a vocabulary the schema was never given. A richer schema capable of expressing "a valid deposit here means a UTXO paying script X" and "a valid deposit here means an event log with topic Y" simultaneously starts to look less like configuration and more like a small domain-specific language, at which point the honest description shifts from "declarative data" to "a restricted programming model," a real distinction even if the line is not sharp.

Third, **the review problem**, developed further in Section 9: even where generation from configuration is technically achievable, nothing about generation reduces the amount of security review a verification component protecting real value requires. If anything, the evidence from mature real-world attempts at this pattern argues the opposite.

**[SPECULATIVE]** The most defensible boundary, stated as a working hypothesis rather than a conclusion: generation stops exactly where syntax ends and semantics begins, and it stops a second time at the custody boundary, which this document's own scaffold places outside an Authorization Domain's concern entirely.

## 8. Prior art

**IBC light client interface (ICS-02, ICS-07).** **[FACT]** A standardized `ClientState`/`ConsensusState`/`ClientMessage` interface, stable for multiple years, that any new light client type implements. **[CONCLUSION]** The single best piece of evidence available anywhere that the "common interface, chain-specific implementation" pattern this document assumes is real and durable at production scale. Also the single best piece of evidence that implementation-level generation has not been achieved by this pattern even after years of sustained investment: 07-tendermint, 06-solomachine, and 11-beefy are each independent, hand-engineered efforts, and industry commentary on IBC specifically has noted that deploying a new light client type is expensive and resource-intensive, not a configuration exercise.

**LLVM TableGen.** Covered in depth in Section 4. **[FACT]** The strongest available example of genuine, working, partial generation from declarative description in a domain of comparable irregularity to blockchain consensus diversity, with a clean, empirically battle-tested line between what gets generated and what stays handwritten.

**zk light client generalization (Succinct Labs' Telepathy for Ethereum; Electron Labs' zkSNARK-based Tendermint-to-Ethereum client; Berkeley RDI's zkBridge).** **[FACT]** Each of these projects builds a succinct proof of a *specific* chain's consensus (Ethereum's sync-committee BLS aggregation in Succinct's case; Tendermint's ed25519 signature aggregation, verified inside a zk circuit and deployed to Ethereum, in Electron Labs' case) rather than a circuit generated from an arbitrary consensus description. **[CONCLUSION]** zkBridge's own framing, that its relay network and proof scheme are "universal" so long as the target chain has *some* light-client protocol to synchronize against, is a claim about the surrounding infrastructure (relaying, recursive proof composition, on-chain verification cost), not a claim that the circuit encoding a specific consensus algorithm's verification logic is itself generated rather than hand-designed per chain. This is consistent with, and independently reinforces, the syntactic-versus-semantic boundary this document draws elsewhere: the infrastructure around verification is more generalizable than the verification logic itself.

**LayerZero V2 (DVNs and adapters) and Axelar.** Covered in Section 4. **[FACT]** LayerZero V2's explicit architectural move, decoupling verification (DVNs) from execution (Executors) behind one Endpoint interface, and allowing third-party verification methods, including at least one zk light client (Polyhedra) and adapters to entirely separate networks (Axelar, Chainlink CCIP), to plug in as interchangeable DVNs, is close in spirit to the Chain Configuration idea, but at the level of *choosing among already-built verification methods* rather than *generating a new one*. **[CONCLUSION]** This is informative in the same direction as the IBC evidence: the industry's most recent, most sophisticated attempt at this exact problem converged on "marketplace of interchangeable, independently engineered verifiers" rather than "generate a verifier from a description," which is either evidence that generation is currently infeasible, or evidence that nobody serving this market has needed it badly enough to build it yet. This document cannot distinguish between those two explanations from the outside, and flags that as an open question.

**Database drivers (ODBC/JDBC) and hardware description (Device Tree).** Covered in Section 4 as informative negative and near-positive cases respectively, not as blockchain-specific prior art. Retained here because both bear directly on where the generic/bespoke boundary should be expected to fall.

**[OPEN]** No academic or industry work matching the phrase "blockchain interface description language" in the specific sense this document investigates, a formal schema from which a new chain's verification logic could be substantially generated, was identified in this research pass. The closest neighbors are the light-client interface standards (IBC) and the zk-circuit generalization projects, both of which, as shown above, standardize or accelerate around a hand-engineered core rather than replacing it. Whether this reflects a genuine gap or a search-scope limitation of this document is itself unresolved.

## 9. Attacking the idea

This section does not defend the concept examined in Sections 1 through 8. It lists every weakness this document could find, on the assumption a reviewer is trying to reject the design.

**Consensus is not stable, and the instability is not hypothetical.** Solana's own governance passed a complete replacement of its consensus mechanism (Alpenglow, replacing both Proof of History and Tower BFT) in September 2025, with mainnet activation expected in 2026 and not yet live as of this writing. Any Chain Configuration pinned to Solana's pre-Alpenglow consensus would need not just regeneration but a fresh governed review, on the same timeline and with the same scrutiny a handwritten replacement would require. Generation reduces authorship effort. It does not reduce review effort, and review effort, not authorship effort, is very plausibly the actual bottleneck for anything that gates real value.

**The class problem front-loads exactly the work generation was supposed to remove.** Every genuinely novel consensus design requires bespoke engineering to become the first instance of a new class, at which point the framework has generated nothing; it has only organized work that still had to happen once. A framework whose value is concentrated in the Nth similar chain and absent for the first of any kind is a real but narrower benefit than "generate an Authorization Domain" suggests on its face.

**A declarative schema can misrepresent security-relevant judgment as a settled value.** "Confirmation depth: 6" looks like configuration. Whether six blocks is actually safe depends on hash rate, cost-of-attack economics, and observed reorg history, none of which are captured by the number itself. A framework that makes filling in a field feel equivalent to having done the underlying security analysis is, if anything, a worse failure mode than an obviously handwritten component that nobody mistakes for pre-validated.

**Configuration becomes a new, less-scrutinized attack surface.** If verification logic is interpreted from a Chain Configuration artifact by generic machinery rather than compiled per chain into dedicated code, the configuration artifact itself becomes a high-value target, and there is a real risk reviewers extend it less scrutiny than a full handwritten implementation precisely because it "looks like data." A wrong Merkle branching-factor parameter or a subtly wrong finality-threshold value could be as catastrophic as a bug in handwritten verification code while being considerably less conspicuous in review.

**The most mature real-world attempts at this exact pattern have not achieved it.** IBC has had years, real funding, and a genuine ecosystem incentive to generate light clients rather than hand-build them, and has not; it has standardized the interface and continued hand-building behind it. LayerZero's most recent architecture converged on a marketplace of independently engineered, interchangeable verifiers rather than a generator. This is not proof that generation is impossible, but it is meaningfully more than a caveat: it is the strongest empirical signal available, and it points away from optimism.

**Custody, excluded from this entire discussion by the design principles document's own boundary, is very plausibly the harder half of the real problem, not the easier one this document has been analyzing.** A fully solved, fully generated verification layer still leaves the Bitcoin-side or Ethereum-side custody mechanism entirely unaddressed, chain-specific by necessity, and not obviously more generalizable than verification is, quite possibly less so, since custody mechanisms (BitVM-style challenge games, threshold-signer committees, lockbox contracts) differ from each other for reasons that have nothing to do with the verification-layer taxonomy this document built. A generated Authorization Domain that omits custody risks being perceived, especially outside a careful reader, as having solved more of the interoperability problem than it actually has.

**Proof-size feasibility is a hard gate that generation does not soften.** Zenon's own account-block data limit and related constants impose a fixed ceiling independent of how elegantly any given chain's verification logic is expressed. Ethereum's own sync-committee light-client design needed real engineering (BLS aggregation specifically) to avoid a client needing to hold tens of megabytes of raw validator keys; that engineering effort is chain-specific and proof-size-driven, not something a configuration schema abstracts away.

**Zenon's own governance model does not obviously reward generation with a faster path to activation.** `RegisterDomain` is administrator-only, and a runtime upgrade (which registering a new Authorization Domain's `stfSpecHash` would resemble) is gated by a mandatory delay no shorter than the withdrawal delay, by design, regardless of how the domain's logic was produced. A generated Authorization Domain would pass through the same time-locked, human-reviewed activation path a handwritten one would. If the goal of generation is faster or cheaper deployment, the protocol's own safety model, correctly, does not offer a shortcut for having gotten there by configuration rather than by hand.

## 10. A proposed future architecture, and a verdict

**[SPECULATIVE, offered as a research direction, not a design commitment.** A layered structure, consistent with everything argued above:

**A small, closed, hand-written set of primitive verifier classes**, each reviewed once and reused: a header parser generic over field layout; a proof-of-work difficulty verifier generic over target encoding; a BFT quorum-certificate verifier generic over validator-set representation; a finality-checkpoint verifier generic over committee rotation and trust-level parameters; a Merkle inclusion verifier and a Merkle-Patricia trie verifier, each generic over hash function and structural parameters; a small family of signature verifiers, one per scheme in active use. This is the layer doing the work TableGen's generated code does: mechanical, reusable, and only added to when a genuinely new consensus *class*, not a new chain within an existing class, appears.

**A declarative Chain Configuration record** selecting among those primitives and supplying their parameters: which consensus-family primitive applies, the header layout, the hash and signature scheme references, the finality predicate's numeric thresholds, and the Merkle structure's parameters. This is the layer doing the work a `.td` file does. Its hash is a natural, though currently unconfirmed, candidate to feed the `stfSpecHash` this Authorization Domain would register under.

**Handwritten semantic glue**, per chain, implementing the deposit-identification predicate and any chain-specific accounting logic the design principles document's Accounting layer already calls for. This layer is not expected to shrink meaningfully as the primitive library grows, because it is not solving the same kind of problem the primitive library solves.

**Custody, entirely outside this driver specification**, exactly as the design principles document already insists, designed and reviewed per chain by whatever mechanism that chain's own properties require.

**[CONCLUSION] Final verdict, in the terms the prompt itself asked this document to resolve.** Authorization Domains are best understood as configurable adapters over a small set of handwritten, reused verification primitives, with true generation, meaning the automatic production of new verification logic from a chain description with no bespoke engineering, not currently achievable and, on the strongest available evidence (a multi-year, well-resourced, real-world attempt at almost exactly this pattern that converged on standardized interfaces rather than generation), not clearly achievable in the near term for any consensus family not already modeled. They are not, however, purely handcrafted either: the syntactic verification layer shows real, defensible structure that a Chain Configuration could capture today, with genuine reuse available wherever chains already share a consensus family, as Cosmos SDK chains under CometBFT and Substrate parachains under a shared relay chain already demonstrate in production.

**[OPEN]** Whether a sufficiently expressive Chain Configuration schema for the semantic/accounting layer is possible at all, or whether that layer is irreducibly bespoke, is not settled by this document and is the most consequential open question it leaves behind. A second, narrower open question: whether the apparent absence of "blockchain interface description language" prior art reflects a genuine gap in the field or a limitation of this research pass.
